# One conditional write owns version and deadline admission

<a id="adr-0013"></a>

- **Decision:** accepted by the owner on 10 October 2026: retain three storage operations and replace `put(record, Option(version)) -> Result(Bool, StoreError)` with `put(record, WriteCondition) -> Result(WriteOutcome, StoreError)`. Conditions are `Absent`, `AtVersion(version)` and `AtVersionBefore(version, deadline)`. Outcomes are `Written`, `VersionConflict` and `DeadlineElapsed`.
- **Ownership:** Warden selects protocol transitions and validity deadlines. Adapters retain opaque records and decide conditional writes atomically. A version mismatch or missing row takes precedence over time. A matching guarded replacement samples the adapter's wall clock under exclusive write authority after lock or queue waiting. Equality is expired. Refusals do not mutate the row.
- **Time:** validity is separate from `Record.expires_at` retention and monotonic request budgets. The deadline protects the decision, not subsequent commit, acknowledgement or provider exchange. A write is confirmed only after the adapter knows it succeeded. Lost acknowledgement remains `StoreOutcomeUnknown`. Durable adapters document their clock and precision; cross-host synchronization and wall-clock steps remain operational concerns.
- **Alternatives:** an optional deadline admits an additional guarded-insert combination or needs runtime rejection. A separate `replace_before` preserves existing calls but creates a second write callback. The unreleased library favors one explicit write contract over migration convenience. Arbitrary predicates and a general transaction interface are unnecessary.
- **Evidence:** the disposable prototype compared three compiled API shapes over one protected memory implementation. Public-consumer scenarios exercised delayed writes, lost acknowledgements, late acknowledgements and recovery. A PostgreSQL 16.15 experiment observed lock waits: a plain UPDATE clock predicate and transaction-start time admitted late writes; locking first and sampling actual time refused them. These are mechanism observations, not production adapter or release certification.
- **Migration:** all adapters and decorators must accept the explicit conditions and return explicit outcomes. There is no weaker compatibility fallback. `testing.check_store` covers guarded refusals, successful writes and concurrency; adapter-specific queue/lock barriers remain necessary. Existing custody transitions use unguarded conditions where late publication is valid.
- **Supersedes:** the Option/Bool interface and unresolved expiry authority in [ADR 0004](0004-sealed-cas-custody.md). Record sealing, pool ownership, uncertainty and tombstone retention remain unchanged. The owner accepted integration on 10 October 2026 after the canonical fast gate passed: 220 library tests, 21 separate-consumer tests, 6 Relay tests, negative compiler fixtures and the native design gate. External adapters require migration; this acceptance does not confer release certification.
