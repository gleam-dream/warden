**Title:** JWKs with `x5c`/`x5t` are rejected, and `key_set.from_json` then
silently returns an empty set for common OIDC providers

**Body:**

Thanks for gose. I'm using it to verify OpenID Connect ID tokens and hit a
limitation that affects common identity providers in practice.

### What happens

A JWK that carries any X.509 member (`x5u`, `x5c`, `x5t`, `x5t#S256`) fails
to parse, even when its key material (`kty`, `n`, `e`, ...) is complete and
valid:

```gleam
import gose/jose/jwk
import gose/jose/key_set

// `bare`: any valid RSA public JWK as JSON.
// `with_x5c`: the same JSON plus "x5c": ["MIIC..."] (its certificate).
jwk.from_json(bare)
// -> Ok(_)
jwk.from_json(with_x5c)
// -> Error(ParseError("unsupported X.509 JWK parameter: x5c"))

key_set.from_json("{\"keys\":[" <> with_x5c <> "]}")
// -> Ok(set) where key_set.to_list(set) == []
```

The same happens with `x5t` alone and with `x5u`.

The README documents this ("JWKs containing X.509 certificate chain
parameters ... are rejected with a parse error"), so this is a request to
reconsider the behaviour rather than a bug report.

### Why it matters

- Keycloak publishes `x5c` and `x5t` on every key of a realm's JWKS by
  default; Microsoft Entra ID and several other providers also include
  `x5c`/`x5t`. (Please double-check the latter against current metadata; I
  have only reproduced the Keycloak case end to end.)
- Because `key_set.from_json` skips invalid keys silently, a provider's JWKS
  "parses successfully" into an empty set. Token verification then fails as
  if the `kid` were unknown, which is hard to diagnose and can trigger
  repeated JWKS refetches.
- RFC 7517 makes these members optional. A consumer that does not use the
  certificate chain (the usual case for OIDC, where trust comes from the
  issuer's TLS-protected `jwks_uri`) can safely use the bare key material.

### Possible directions (any would help)

1. **Ignore X.509 members when parsing** and use the key material, without
   validating the chain. Document that gose does not validate the
   certificate. Optionally expose the raw `x5c`/`x5t` values so callers can
   do their own checks.
2. **Ignore them, but check consistency cheaply:** RFC 7517 §4.7 says the key
   in the first `x5c` certificate MUST match the JWK's key material. Comparing
   the first certificate's SubjectPublicKeyInfo with the parsed key (no chain
   or path validation) would catch inconsistent JWKs without becoming a PKI
   library. `x5t`/`x5t#S256` could likewise be checked against that
   certificate.
3. **Keep strict parsing by default, add a lenient entry point**, e.g.
   `jwk.from_json_ignoring_x509` / `key_set.from_json_ignoring_x509`.
4. Independently of the above: let `key_set` report skipped keys and why
   (e.g. a variant that returns `#(JwkSet, List(#(Int, GoseError)))`), so an
   empty or partial set is not silent.

### Current workaround

Remove `x5u`, `x5c`, `x5t` and `x5t#S256` from each JWK object before calling
`jwk.from_dynamic`/`from_json`. This is safe only for callers that never rely
on the certificate chain.

I'm happy to send a PR for whichever direction you prefer.
